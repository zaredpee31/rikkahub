# Aoi&C 记忆系统改造方案

借鉴 SullyOS 的房间 + 门牌 + 向量召回，代码全部自写，不复制其源码（它是源码可见许可，不允许搬代码）。

状态：待小葵确认，未改代码。分支 feature/companion-messages，数据库现为第 32 版。

## 一、要解决的问题

现在的记忆是一份份 Markdown 文件。发消息时只把 profile 和 preferences 整份塞进提示词，其余只给标题和关键词，得助手自己意识到"这个可能记过"才去读。几天前的小事接不上，根子在这。

整理提示词也写得太严，原话是大多数时候只记 0 到 2 条、经常 0 条，宁可漏也不乱记，所以闲聊小事基本进不去。

## 二、房间

- 客厅 living_room：日常闲聊、近期小事。有容量上限，衰减快。
- 卧室 bedroom：两个人之间的感情和羁绊。衰减慢。
- 书房 study：干活、学习、技能、项目。衰减慢。
- 用户房 user_room：小葵的个人信息和习惯。衰减慢。
- 自我房 self_room：阿辞对自己的认知。不衰减。
- 阁楼 attic：没消化的困惑。先做可选，第一版可以不做。
- 窗台 windowsill：期盼和想一起做的事。先做可选。

第一版先做前五个房间，阁楼和窗台留接口但不实现。

## 三、门牌

门牌是从房间里沉淀出来的稳定事实，每轮直接注入提示词，不走召回，不衰减。解决向量召回"抽卡"的问题：稳定的事不靠这次搜到什么。

- 用户房门牌「TA 的事」：小葵的稳定事实。现有 profile 迁到这里。
- 自我房门牌「我是谁」：阿辞的自我认知。
- 卧室门牌「我们之间」：关系的质地，只描述现象，不给关系起名字。
- 书房门牌「我的领域」：会什么、在做什么。

preferences 是说话和相处的规则，单独做一块常驻注入，不进召回，也不进门牌。

## 四、消息端和窗口端

这是这次最重要的分野，按小葵的要求来。

消息端（companion，日常陪伴的阿辞）：
- 自动整理：对话攒到一定量后，用记忆整理模型把这段聊天写成一条条回忆，分房间，转向量存库。
- 自动召回：每次发消息前，拿最近几条消息去向量库里搜，语义为主、关键词为辅，挑出相关的几条塞进提示词。
- 门牌每轮常驻。

普通窗口（干活、查东西、改东西、狼人杀）：
- 不自动召回，不自动整理。玩一局狼人杀不会变成一条记忆，改代码的流水账也不会进去。
- 门牌照样每轮常驻，所以窗口里的阿辞知道两个人是怎么回事、以前干过什么，不会变成不认识人的工具人。
- 保留手动记和手动查。做好一个东西，说"把这个记一下"，就写成房间里的一条。

记忆库只有一个，两端共用。

## 五、老记忆怎么处理

格式不能直接兼容：现在是 Markdown 文件，新的是分房间的向量节点。

做法：
1. 迁移前先把全部现有记忆文件导出一份备份，原文件不动，坏不了。
2. 逐条读出来，按内容归到房间或门牌。稳定事实进门牌，具体经历进对应房间。
3. 归类由整理模型做一遍初稿，小葵可以在界面上改。
4. 提供手动添加入口：选房间，写一句话，存进去，自动转向量。一条条粘贴的笨办法也走这个入口。
5. 旧的 Markdown 文件保留只读，不删。新系统跑稳之前，旧的注入逻辑先留着做兜底，确认没问题再撤。

## 六、模型和向量

- 整理走现有的"记忆整理模型"槽位，没设就用快速模型。挂个便宜模型即可。
- 向量另加一个 embedding 配置：地址、密钥、模型名。OpenAI 兼容格式，硅基流动可以直接填。底层 OpenAIProvider 已实现 generateEmbedding，app 里还没人调用，接上即可。
- embedding 没配时，自动召回降级为不做，门牌和手动记不受影响，不报错打断聊天。

## 七、时间

现有的时间提醒按消息间隔插入，够用，这次不动。

## 八、存储

新增两张表，数据库从 32 升到 33：
- memory_node：id、房间、正文、重要性、情绪、标签、创建时间、来源（哪段对话）、向量。
- memory_plate：房间、条目列表、更新时间。

向量存在本机数据库里，不上传。召回在手机本地算余弦相似度，记忆量不大，不需要单独的向量数据库。

## 九、改动落点

- 数据层：data/db 新增 entity、dao，AppDatabase 升版本加迁移。
- 召回与整理：data/ai 下新增 memorypalace 包，包含提取、向量化、召回、门牌合并。
- 注入：ChatRequestFactory 里按入口区分。companion 走召回加门牌，普通窗口只走门牌。
- 触发：companion 回复落库后检查是否达到整理阈值；普通窗口不触发。
- 工具：MemoryTools 增加手动记一条、手动查的入口，窗口端保留。
- 界面：记忆页增加房间列表、单条详情、手动添加、embedding 配置、迁移向导。

## 十、不做的

- 不复制 SullyOS 任何代码，只借结构。
- 不做它的七房间全套，阁楼和窗台第一版留空。
- 不做扩散激活、情绪反刍这些仿脑机制，收益不明确，先把召回跑通。
- 不改 Caddy、不碰服务器上现有服务。
- 记忆内容不上传到任何地方，embedding 请求只发正文给配置的接口。

## 十一、风险

- 整理和召回都要调模型，会花 token。整理用便宜模型，召回的 embedding 开销很小。
- 向量召回本质是按相似度抽，不保证每次都命中。门牌兜住稳定事实，小事靠召回，这是这套方案的上限，先说清楚。
- 迁移归类可能分错房间，所以要能在界面上改、能手动加。
- 改动跨数据库、注入、界面，需要打包到手机实测，不能只看编译过。
